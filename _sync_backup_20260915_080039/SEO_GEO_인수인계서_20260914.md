## 2. 가장 중요한 발견 — 구조화 데이터가 전부 무효였다

### 증상

`templates/form.html` 등이 JSON-LD를 `{{ jsonld }}` 로 출력하고 있었다.
Jinja 자동 이스케이프가 걸려 큰따옴표가 전부 `&#34;` 로 바뀌어 나갔다.

```html
<script type="application/ld+json">
{&#34;@context&#34;: &#34;https://schema.org&#34;, &#34;@type&#34;: &#34;DigitalDocument&#34; …
</script>
```

### 왜 치명적인가

`<script>` 요소 안에서는 브라우저와 파서가 **문자참조(`&#34;`)를 되돌리지 않는다.**
따라서 검색엔진이 JSON을 파싱하지 못하고 구조화 데이터 전체를 버린다.
2026-09-13에 넣은 `DigitalDocument`·`FAQPage`, 계열·주제모음의 `ItemList`가
**배포된 내내 하나도 읽히지 않고 있었다.**

### 조치

`{{ jsonld | safe }}` 로 수정(`form.html`·`series.html`·`collection.html`).
수정 후 전 페이지 780블록이 전부 파싱 성공.

### 재발 방지

1. `scripts/build_site.py` 에 `jd()` 헬퍼를 두고 주석에 이 사고를 명시했다.
   JSON-LD를 만들 때는 `jd()` 를 쓰고 템플릿에서는 반드시 `| safe` 를 붙인다.
2. **검증 스크립트에 JSON 파싱 테스트를 넣어야 한다** — 현재는 수동 확인에 의존한다.
   (잔여 업무 C1 참조)

> 교훈. 이번 건은 "만들어 넣었으니 됐다"고 믿고 **출력물을 파싱해 본 적이 없어서**
> 이틀간 방치됐다. 구조화 데이터·피드·사이트맵처럼 기계가 읽는 산출물은
> 사람 눈으로 보지 말고 **파서에 넣어 봐야** 한다.

## 9. 개발가이드 반영 필요 항목

본 프로젝트는 자동매매봇 개발가이드(GUIDEBOOK)와 별개 라인이지만, 아래는 재사용 가치가 있다.

1. **기계가 읽는 산출물은 파서에 넣어 검증한다.** JSON-LD·사이트맵·RSS·설정 파일은
   사람 눈으로 보면 멀쩡해 보인다. 이번에 구조화 데이터가 이틀간 무효였던 이유가 이것이다.
   생성 직후 `json.loads` / `xml.etree.parse` 를 통과시키는 검사를 **생성기와 같은 커밋에**
   넣는다.
2. **템플릿 엔진의 자동 이스케이프는 HTML 본문 기준이다.** `<script>`·`<style>` 안에
   넣는 값은 이스케이프 규칙이 다르다. 자동 이스케이프를 켠 채 스크립트 블록에 값을
   넣을 때는 반드시 출력물을 확인한다.
3. **환경을 타는 표준함수를 쓰지 않는다.** `strftime("%a"/"%b")`(로캘),
   경로 구분자, 줄바꿈. 빌드가 두 개 이상의 OS에서 돌아가는 프로젝트라면 더 그렇다.
4. **외부 콘솔의 진단 화면은 "언제 수집한 데이터인지"를 먼저 본다.**
   빙의 Bing Index 탭, 네이버의 색인 상태 확인, 구글의 발견 페이지 수는 전부
