# 서식 명세(YAML) 작성 규칙서

「무료서식 다운로드」 사이트의 서식은 **YAML 명세 파일 1개**로 정의한다.
명세를 `specs/{id}.yaml`로 저장하면 `scripts/build_form.py`가 PDF·DOCX·HWPX·미리보기·카탈로그를
모두 자동 생성한다. 작성자는 **명세만** 쓰면 되고 렌더링 코드는 건드리지 않는다.

## 1. 파일 위치와 이름

- 경로: `specs/{id}.yaml`
- `id`는 영문 소문자·숫자·하이픈만. **파일명과 `id` 필드가 반드시 일치**해야 한다.
- id는 서식 내용을 알 수 있게 짓는다. 예: `resignation-letter`, `meeting-minutes`, `expense-report`.

## 2. 머리말(메타데이터) 필수 필드

```yaml
id: meeting-minutes                 # 파일명과 동일
title: 회의록                        # 사이트에 표시되는 한국어 정식명
category: corp                      # categories.json의 대분류 key
subcategory: admin                  # categories.json의 중분류 key
tags: [회의록, 회의결과, 회의일지, minutes]   # 검색 별칭 3~6개
summary: 회의 일시·참석자·안건별 논의 내용과 결정사항·후속조치를 기록하는 회의록 양식입니다.
usage: >
  실제 사용 상황과 작성 요령을 3~5문장으로 쓴다. 상세 화면에 노출되고 검색 유입의
  핵심이 되므로 성의 있게 쓴다. "무엇에 쓰는 서류인지 / 어떻게 채우는지 /
  주의할 점" 순서로 쓴다.
source: original                    # original | law-standard | public-license
featured: false                     # 메인 노출 10종만 true
target_pages: 1                     # 목표 페이지 수 (넘치면 자동 축소, 0이면 자동 산출)
series: resume                      # (선택) 같은 서식의 실무 변형 묶음 키
series_name: 이력서                  # (선택) 계열 표시명
variant: 경력용                      # (선택) 이 서식의 변형 이름
variant_rank: 2                     # (선택) 계열 안에서의 나열 순서 (작을수록 먼저)
variant_use: 경력직 이직에 씁니다.     # (계열 서식은 필수) 비교표의 "이럴 때 쓰세요" 한 줄
howto:                              # (필수) 상세 화면 "작성 순서"
  - 회의 일시와 장소, 참석자를 적습니다.
  - 안건별로 논의 내용을 요약해 적습니다.
faq:                                # (필수) 상세 화면 "자주 묻는 질문"
  - q: 불참자도 참석자란에 적나요?
    a: 불참자는 따로 적지 않고, 필요하면 배포처에 이름을 남깁니다.
blocks:
  - ...
```

### 계열(series) — 하나의 서식을 실무 버전별로 나눌 때

같은 용도의 서식이라도 실무에서는 상황별로 항목이 다르다. 이력서라면 신입용은 학력·대외활동이
크고 경력용은 경력기술과 프로젝트가 커야 한다. 이런 변형끼리는 `series`를 같은 값으로 두면
상세 화면에 **"이력서 다른 버전"** 목록이 함께 표시되어 사용자가 바로 갈아탈 수 있다.

- `series`는 영문 소문자·하이픈. 계열 안의 모든 서식이 같은 값을 써야 한다.
- `series_name`은 계열 이름(한국어). 계열 안에서 **모두 같은 값**을 쓴다.
- `variant`는 이 서식만의 이름. 제목의 괄호 안과 같게 쓴다. 예: `title: 이력서 (경력용)` → `variant: 경력용`
- 변형은 **항목 구성이 실제로 달라야** 한다. 제목만 바꾼 같은 표는 만들지 않는다.

`category` / `subcategory` 유효값은 `catalog/categories.json`에서 확인한다.

| 대분류 | key | 중분류 key |
|---|---|---|
| 기업 | `corp` | `hr`(인사·노무) `admin`(총무·행정) `finance`(회계·세무) `sales`(영업·마케팅) `startup`(창업·법인) |
| 법률 | `legal` | `contract`(계약) `notice`(통지·증명) `litigation`(소송·민원) |
| 공공 | `public` | `civil`(민원·신고) `consent`(신청·동의) |
| 부동산 | `estate` | `lease`(임대·매매) |
| 개인 | `personal` | `career`(취업·경력) `life`(생활·가정) |
| 교육 | `edu` | `school`(학교·학원) |
| 의료·복지 | `welfare` | `consent`(동의·신청) |

법정 서식을 참고한 경우 `source: law-standard`와 함께 `source_note`에 근거 법령을 적는다.

## 3. 블록 타입 레퍼런스

블록은 `blocks:` 아래에 위에서 아래 순서로 렌더링된다.

### doc_title — 문서 제목 (서식마다 맨 위에 1개)
```yaml
- type: doc_title
  text: 회의록
  spaced: true      # 8자 이하면 글자 사이를 벌린다. 긴 제목은 false
```

### subtitle — 구역 제목 (악센트 바 + 밑선이 자동으로 붙는다)
```yaml
- type: subtitle
  text: 1. 회의 개요
```

### para — 일반 문단
```yaml
- type: para
  text: 위 기재사항은 사실과 다름이 없음을 확인합니다.
  align: center     # left | center | right | both
  size: 11          # 생략 시 10.5
```

### grid — 라벨-값 격자표 (인적사항·기본정보에 사용)
```yaml
- type: grid
  widths: [15, 35, 15, 35]     # 컬럼 비율(합 100). 셀 개수와 길이가 같아야 한다
  label_cols: [0, 2]           # 라벨(음영+굵게)로 처리할 컬럼 번호
  row_height_mm: 8             # 행 최소 높이
  merges:                      # [시작행, 시작열, 끝행, 끝열] — 선택
    - [1, 1, 1, 3]
  rows:
    - ["회의명", "", "일시", ""]
    - ["장소", "", "", ""]
```
- 값이 들어갈 칸은 `""`(빈 문자열)로 둔다. 사용자가 손으로 채우는 칸이다.
- `label_cols`를 생략하면 짝수 컬럼(0,2,4…)이 자동으로 라벨이 된다.
- `merges`로 병합한 칸은 한 칸처럼 넓어진다. 주소·이메일처럼 긴 값에 쓴다.

### table — 머리글 + 빈 입력행 표 (목록형 데이터에 사용)
```yaml
- type: table
  widths: [10, 30, 40, 20]
  header: ["No", 안건, 논의 내용, 결정사항]
  empty_rows: 5                # 빈 입력행 개수
  row_height_mm: 8
  body_align: center           # 미리 채운 rows의 정렬 (선택)
```
- 머리글은 짙은 네이비 배경 + 흰 글자로 자동 처리된다.
- **`"No"`처럼 YAML이 불리언으로 읽는 값은 반드시 따옴표로 감싼다.** (`No`, `Yes`, `On`, `Off`, `Y`, `N`)
  따옴표를 빼면 `False`로 출력되고, 빌드 시 명세 검증에서 오류로 막힌다.

### textbox — 자유기술란 (서술형 답변 칸)
```yaml
- type: textbox
  hint: "논의 배경과 경과를 시간순으로 작성하십시오."   # 박스 위 작은 회색 안내문 (선택)
  height_mm: 30                                    # 박스 높이
```
- **단일 칸 `table`을 자유기술란으로 쓰지 말 것.** 머리글이 짙은 띠로 나와 어색하다. 반드시 `textbox`를 쓴다.

### article — 계약서 조항 (조 제목 + 본문 여러 줄)
```yaml
- type: article
  heading: 제1조 (목적)
  lines:
    - "본 계약은 …을 목적으로 한다."
    - "제2항 내용."
```

### kv_list — 점(·) 목록
```yaml
- type: kv_list
  items:
    - "임금은 근로자에게 직접 지급한다."
    - "지급일이 휴일인 경우 그 전일에 지급한다."
```

### date_line / sign_line / notice / spacer / page_break
```yaml
- type: date_line                    # "20        년        월        일" 가운데 정렬
  text: 20        년        월        일   # 다르게 쓰려면 지정 (선택)

- type: sign_line
  label: 작성자                       # 1명
- type: sign_line
  labels: ["위임인", "수임인"]          # 여러 명

- type: notice
  text: 제출 전 사본을 보관하십시오.      # 하단 작은 회색 안내. 앞에 ※ 자동 삽입

- type: spacer
  height_pt: 8

- type: page_break                   # 여러 장 서식에서 장 구분
```

## 3-1. 미리보기 작성 예시 (sample) — **모든 서식에 반드시 넣는다**

사이트의 미리보기 이미지는 **빈 양식이 아니라 예시가 채워진 화면**이다. 사용자가 "이 칸에
뭘 쓰는 거지"를 고민하지 않도록 하기 위한 것이고, 검색 유입 후 체류·다운로드로 이어지는
가장 큰 요인이다. **다운로드되는 PDF·DOCX·HWPX는 언제나 빈 양식**이며 예시는 미리보기
이미지에만 들어간다. 빌드가 예시판을 따로 한 번 더 렌더링하므로 명세 한 곳만 쓰면 된다.

예시 글자는 자동으로 **파란 계열 색**으로 나가 라벨·안내문과 구분된다.

### grid — `sample_rows`

`rows`와 **행 수·셀 수가 같은** 표를 하나 더 쓴다. 라벨 칸은 `""`로 두고 **빈 입력칸에만**
값을 넣는다(라벨 칸에 값을 넣어도 무시된다). 병합된 칸은 **좌상단 칸**에 값을 넣는다.

```yaml
- type: grid
  widths: [15, 35, 15, 35]
  row_height_mm: 8
  merges: [[1, 1, 1, 3]]
  rows:
    - ["회의명", "", "일시", ""]
    - ["장소", "", "", ""]
  sample_rows:
    - ["", "2분기 마케팅 전략 회의", "", "2026-09-10 14:00"]
    - ["", "본사 3층 회의실 A", "", ""]
```

### grid — `photo_cell` (증명사진 칸)

사진란이 있는 서식(이력서 등)은 **병합된 사진 칸의 좌상단 좌표**를 적는다. 예시 미리보기에서만
사람 실루엣이 들어가고 빈 양식에는 들어가지 않는다. `photo_mm`은 [가로, 세로] mm이며
병합 칸보다 **작게** 잡는다(기본 26×34).

```yaml
  photo_cell: [0, 6]
  photo_mm: [24, 32]
```

사진이 칸보다 크면 렌더러가 **비율을 유지한 채 칸 안에 맞게 자동으로 줄인다**
(병합 행 높이 합 − 2mm, 열 폭 − 3mm, 1페이지 자동 맞춤 배율까지 반영). 그래도 명세에서는
`행 수 × row_height_mm` 보다 작은 세로값을 쓰는 것이 원칙이다 — 4행 × 7.5mm 칸이면 24×28 정도.
(2026-09-14 이력서 경력용·신입용·서술형·입사지원서 4종에서 32mm 사진이 30mm 칸을 넘어
미리보기 오른쪽이 잘려 보이던 결함을 이 자동 맞춤으로 고쳤다.)

### table — `sample_rows`

`empty_rows`로 만든 빈 입력행을 **위에서부터** 채운다. 셀 개수는 `header`와 같아야 하고,
행 수는 `empty_rows` 이하여야 한다. **전부 채우지 말고 마지막 1행 정도는 비워 두는 편이**
"여기에 계속 쓰면 된다"가 전달돼 좋다.

```yaml
- type: table
  widths: [10, 30, 40, 20]
  header: ["No", 안건, 논의 내용, 결정사항]
  empty_rows: 4
  sample_rows:
    - ["1", "3분기 광고 예산", "채널별 배분안 검토", "SNS 비중 40%로 상향"]
    - ["2", "신제품 출시 일정", "생산 일정 2주 지연", "10월 2주차로 연기"]
```

### textbox — `sample_text`

박스 안에 들어갈 예시 문장. 박스 높이에 비해 길면 페이지가 넘치므로 **`height_mm × 8자`**
이내로 쓴다(30mm면 240자). 줄바꿈은 `\n`을 쓰지 말고 한 문단으로 쓴다.

### para / date_line — `sample_text`, sign_line — `sample_names`

```yaml
- type: date_line
  sample_text: 2026 년    9 월    13 일
- type: sign_line
  labels: ["위임인", "수임인"]
  sample_names: [홍길동, 김서연]
```

### 예시값 작성 규칙

1. **실명·실제 상호를 쓰지 않는다.** 사람은 `홍길동 김서연 박민준 이수현`, 회사는
   `(주)한빛커머스 (주)새길데이터 한빛물산`, 이메일은 `@example.com`, 전화는
   `010-1234-5678` 같은 가공 값만 쓴다. 사업자등록번호·계좌번호는 `000-00-00000`처럼
   자리만 표시한다.
2. **한 칸에 한 줄로 들어갈 길이**로 쓴다. 칸 폭(%)×1.7 글자 수를 넘기면 줄바꿈이 생겨
   표가 커지고 페이지가 넘친다. 넘치면 빌드가 예시판만 자동 축소하지만, 짧게 쓰는 편이 낫다.
3. **날짜는 2026년 기준**으로 쓴다(예: `2026-09-10`). 미래 시점은 쓰지 않는다.
4. **금액은 현실적인 범위**로 쓴다. 계약서 예시에 과장된 금액을 넣지 않는다.
5. **법률 판단이 들어가는 칸(분쟁 내용, 청구 취지 등)은 예시를 짧고 중립적으로** 쓴다.
   특정 사건을 단정하는 문장은 넣지 않는다.

## 3-2. 상세 화면 본문 (`howto` · `faq` · `variant_use`) — **모든 서식에 반드시 넣는다**

다운로드 버튼만 있는 페이지는 사람이 3초 만에 떠난다. 상세 화면에 **작성 순서**와
**자주 묻는 질문**이 있으면 머무는 시간과 한 번에 보는 페이지 수가 늘고, 검색 유입도 함께 는다.

다만 이 사이트의 방문자는 "빨리 받아서 채우려는 사람"이다.
**복잡하거나 어려워 보이면 역효과**이므로, 길게 쓰는 것이 아니라 **짧게 끊어 쓰는 것**이 규칙이다.

```yaml
variant_use: 경력직 이직에 씁니다.        # 계열 서식만. 40자 이내 한 줄
howto:
  - 사진은 3개월 이내에 찍은 것을 붙입니다.
  - 학력은 최종학력부터 거꾸로 적습니다.
  - 경력은 최근 근무지부터 거꾸로 적습니다.
faq:
  - q: 사진은 꼭 붙여야 하나요?
    a: 채용공고에 요구가 없으면 비워도 됩니다. 사진란이 있는 서식이라면 넣는 쪽이 무난합니다.
  - q: 경력이 없으면 어떻게 적나요?
    a: 경력란에 "해당 없음"이라고 적거나, 인턴·아르바이트 경험을 기간과 함께 적으면 됩니다.
```

### 분량 규칙 (check_spec.py가 검사한다)

| 항목 | 개수 | 길이 | 비고 |
|---|---|---|---|
| `howto` | 3~5단계 | 한 단계 **60자 이내** | 한 단계 = 한 문장. 마침표는 끝에 하나만 |
| `faq.q` | 2~4문항 | **34자 이내** | 반드시 물음표로 끝낸다 |
| `faq.a` | — | **140자 이내** | 1~2문장 |
| `variant_use` | 계열 서식 필수 | **40자 이내** | 계열 비교표 `/series/<key>/`에 그대로 나간다 |

### 쓰는 방법

1. **howto는 손이 움직이는 순서**로 쓴다. 항목 설명이 아니라 "무엇을 먼저 적는가"이다.
   화면에는 번호가 붙은 목록으로 나가므로 각 줄이 한 눈에 읽혀야 한다.
2. **법 조문 번호·전문용어를 쓰지 않는다.** 꼭 필요하면 쉬운 말로 풀어 쓴다.
   (예: "근로기준법 제17조에 따라" → "근무 조건은 문서로 남겨야 하므로")
3. **faq는 그 서식에서 진짜 헷갈리는 것**만 쓴다. 화면에서는 접힌 상태(아코디언)로 나가고
   첫 문항만 펼쳐진다. "한글 파일이 안 열린다" 같은 파일 형식 질문은 서식마다 넣지 않는다.
4. **variant_use는 같은 계열의 다른 버전과 겹치지 않게** 쓴다. 비교표에서 나란히 놓이므로
   "이 버전을 골라야 하는 이유"가 한 줄로 구별되어야 한다. 문체는 `~씁니다`로 통일한다.
5. 문체는 `~합니다` 존댓말. 값에 콜론(`:`)이 들어가면 큰따옴표로 감싼다.

`faq`를 넣으면 상세 페이지에 FAQ 구조화 데이터(FAQPage)가 자동으로 붙는다.
따라서 **사실과 다른 답을 쓰면 안 된다.** 확신이 없으면 그 문항을 빼거나
"제출처 규정을 확인하십시오" 수준으로 쓴다.

### "이 서식에 들어 있는 항목"은 자동으로 만들어진다 (따로 쓰지 않는다)

상세 화면의 **이 서식에 들어 있는 항목** 목록은 `blocks`에서 빌드가 직접 뽑는다.
명세에 따로 적을 필요가 없다.

| 블록 | 목록에 들어가는 것 |
|---|---|
| `subtitle` | 구역 제목 (굵은 글씨 줄) |
| `grid` | `label_cols` 위치의 라벨 칸 |
| `table` | 머리글(`header`) |
| `article` | 조 제목(`heading`) |
| `textbox` | 그 구역에 채울 항목이 없을 때 `hint` 문구 |

그래서 **`subtitle`과 `textbox`의 `hint`를 성의 있게 쓰면 그대로 상세 화면 본문이 된다.**
자기소개서처럼 서술형 칸만 있는 서식은 이 안내문이 사실상 유일한 본문이므로 특히 중요하다.

값 칸(`""`), 일련번호 머리글(`No`·`번호`·`구분`·`비고` 등), 24자가 넘는 긴 문장은 자동으로 빠진다.
목록은 구역 12개·항목 48개까지만 나간다(그 이상은 화면에서 읽히지 않는다).

### 도장 위젯(`seal`)도 자동이다

상세 화면의 **이 서식에 찍을 도장 만들기** 위젯(→ `/tools/stamp/`)은 카탈로그의 `seal` 값으로 붙는다.
`sign_line` 블록이 있거나 본문 어디든 `(인)`·`(서명`·`날인`·`직인`·`인감` 글자가 있으면 빌드가 `true`로
넣는다(`form_spec.seal_of`). 명세에 따로 적을 것은 없다. 가계부·시간표처럼 서명 칸이 없는 서식에는 붙지
않는다. 글만 고쳤을 때는 `sync_meta.py`가 이 값도 함께 갱신한다.

## 3-3. `related` — 함께 쓰는 서식 (**모든 서식에 반드시 넣는다**)

상세 화면 아래의 **함께 찾는 서식** 10칸을 채우는 데 쓴다. 앞쪽은 여기 적은 순서대로
들어가고, 남는 칸만 빌드가 본문 유사도로 채운다.

```yaml
related: [handover-report, severance-calculation, career-certificate, asset-handover]
```

규칙:

- **2~4개.** 확실한 것만 적는다. 억지로 4개를 채우지 않는다.
- **글자가 겹치는 것이 아니라 "그 다음에 필요한 것"을 적는다.** 사직서 → 인수인계서·퇴직금
  정산서처럼 제목은 안 겹쳐도 실제로 이어 쓰는 서식이 정답이다. 제목이 비슷한 것은
  빌드가 유사도로 알아서 찾으므로 여기 적을 이유가 없다.
- **같은 `series`의 서식은 적지 않는다.** 계열 변형은 상세 화면 위쪽에 이미 나온다.
- 카탈로그에 실제로 있는 id만 적는다. 없는 id를 적으면 `check_spec.py`가 잡는다.

## 3-4. 주제 모음(`catalog/collections.json`) — 새 서식을 만들면 확인한다

`collections.json`은 **분류가 달라도 한 가지 일에 연달아 쓰는 서식**을 묶은 목록이다
(`/collection/<key>/`). 계열 허브가 "같은 서식의 변형"을 세로로 묶는다면, 주제 모음은
"일의 흐름"을 가로로 묶는다.

새 서식을 만들었을 때:

1. 기존 모음 중 그 일에 들어가는 것이 있으면 `ids`에 **흐름 순서대로** 끼워 넣는다.
2. 맞는 모음이 없으면 그냥 두어도 된다. 모음은 억지로 늘리지 않는다.
3. 한 모음은 최소 4종이어야 하고, 없는 id를 적으면 빌드가 멈춘다.

### 글만 고쳤을 때는 다시 렌더링하지 않는다

`howto`·`faq`·`summary`처럼 화면에 나가는 글만 고쳤다면 PDF·DOCX·HWPX를 다시 만들 이유가 없다.

```bash
python scripts/sync_meta.py <서식id>   # 카탈로그의 글 필드만 갱신 (전체도 1초)
python scripts/build_site.py           # 사이트 재생성
```

`blocks:`(레이아웃)를 고쳤다면 `sync_meta.py`로는 반영되지 않는다 — `build_form.py`를 써야 한다.

## 4. 서식 설계 원칙 (반드시 지킬 것)

1. **표준 구성을 지킨다.** 실무에서 쓰이는 항목을 빠뜨리지 않는다. 법정서식이 있는 경우
   해당 법령의 필수 기재사항을 모두 넣는다.
2. **주민등록번호를 넣지 않는다.** `생년월일`로 대체한다. 빌드 시 자동 검수에서 차단된다.
3. **1페이지 원칙.** 계약서·증명서가 아닌 일반 서식은 `target_pages: 1`을 목표로 한다.
   넘치면 `empty_rows`를 줄인다. 자동 축소는 간격만 줄이므로 내용이 너무 많으면 실패한다.
4. **자유기술란은 `textbox`, 목록은 `table`, 기본정보는 `grid`** 로 명확히 구분한다.
5. **`widths` 합은 100**, 그리고 `rows`의 각 행 길이는 `widths` 길이와 반드시 같아야 한다.
6. **서명·날인란과 날짜란**을 빠뜨리지 않는다. 제출용 서식은 거의 모두 필요하다.
7. **`summary`와 `usage`는 검색 유입의 핵심**이다. 서식명만 반복하지 말고 실제 사용 상황과
   주의사항을 구체적으로 쓴다.
8. 법률 판단이 필요한 내용(구체적 분쟁 대응, 세액 계산 등)은 서식 틀만 제공하고 본문에
   단정적으로 쓰지 않는다. 필요하면 `notice`로 "제출처 규정을 확인하십시오" 수준으로 안내한다.

## 5. 작성 후 확인 절차

```bash
python scripts/check_spec.py {id}            # 문법·분류·예시 모양 검사 (렌더링 없이 빠름)
python scripts/build_form.py {id}            # 해당 서식만 빌드
python scripts/build_form.py                 # specs 전체 순차 빌드
python scripts/build_all_parallel.py --jobs 4  # 전체 병렬 빌드 (200종 이상이면 이쪽)
```

`build_all_parallel.py` 는 명세를 조각으로 나눠 동시에 돌리고 카탈로그를 합친다.
조각마다 기존 `catalog.json` 을 출발점으로 복사하므로 `created_at` 과 `downloads` 가 보존된다.
`--jobs` 는 **CPU 코어 수 ×2 를 넘기지 말 것** — LibreOffice가 CPU를 크게 쓴다.

출력에서 다음을 확인한다.

- `[완료] 1p` — 목표 페이지 수 안에 들어왔는지
- `[자동맞춤] 간격 85%로 축소` — 85% 미만까지 축소되면 내용이 과다하므로 `empty_rows`를 줄인다
- `[경고]` — 항목 누락·개인정보·파일 크기 문제. 경고가 남은 채로 완료하지 않는다

생성물은 `public/files/{id}/`에 `{id}.pdf` `{id}.docx` `{id}.hwpx` `preview-1.webp`로 저장되고
`catalog/catalog.json`에 자동 등록된다.
