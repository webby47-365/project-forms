# 일일 서식 추가 에이전트 운영 지침 (정본)

이 문서는 매일 08:00(KST) 실행되는 **GitHub Actions 워크플로**(`.github/workflows/daily-forms.yml`)의
**지침 정본**이다. 워크플로의 프롬프트는 "이 문서를 읽고 그대로 수행하라"로 짧게 두고,
절차 변경은 이 문서만 고친다.

## 0. 전제

- 실행 환경: **GitHub Actions 러너**(ubuntu-latest). 저장소가 이미 체크아웃되어 있고
  현재 폴더가 저장소 루트다. **클론할 필요 없다.** 관리자 컴퓨터가 꺼져 있어도 동작한다.
- 배포 경로: 커밋·푸시 → `deploy-pages` 워크플로가 자동으로 깨어나 GitHub Pages에 반영
  (약 1~2분). 푸시가 곧 배포다.
- 정본 흐름: GitHub `main` → 관리자가 로컬(`C:\Project_Forms`)로 당겨 맞춘다. 10절 참조.
- 하루 산출: **신규 서식 5종 + 정보형 가이드 1편** (서식 주간 상한 30종, 가이드 주간 상한 7편)
- **목표는 꾸준한 증가다.** 경쟁 사이트는 수천 종을 갖추고 있다. 매일 채우는 것이 원칙이며,
  "만들 것이 없다"는 결론은 마지막 수단이다. 후보가 마르면 6절(계열 변형)에서 반드시 채운다.
- **승인 절차 없음**: 생성한 서식을 스스로 검수해 통과한 것만 등록한다(4절).
- 토큰·키는 GitHub 저장소 Secrets에만 두고, 이 문서·저장소·로그에 절대 기재하지 않는다.

글꼴 대체 설정(맑은 고딕 → Noto Sans CJK KR)도 적용되어 있다.

## 1-1. 밀린 방문자 요청 먼저 (가장 우선)

방문자 요청은 즉시 제작(`request-form.yml`)이 맡지만, 시간당·하루 상한을 넘긴 요청은
접수함에만 쌓여 있다. **오늘 만들 5종 중 앞자리를 이 요청들이 가져간다.**

```bash
# 접수 주소는 catalog/requests.json 의 endpoint 와 같다
python - <<'EOS'
import json, urllib.request
cfg = json.load(open('catalog/requests.json', encoding='utf-8'))
if cfg.get('endpoint'):
    with urllib.request.urlopen(cfg['endpoint'], timeout=20) as r:
        print(r.read().decode('utf-8'))
EOS
```

- 돌아온 `pending` 목록을 오래된 순으로 본다.
- `request_form_agent.md` **2절의 거르는 기준**을 똑같이 적용한다(이미 있음·법정 서식·
  특정 기업 양식·개인정보·서식 아님·장난).
- 통과한 요청을 **먼저** 만든다. 명세에 `from_request: true` 를 넣는다.
- 요청으로 5종을 채웠으면 아래 수요 조사는 건너뛴다. 모자란 만큼만 자체 후보로 채운다.
- 접수 주소가 비어 있거나 조회에 실패하면 이 절을 건너뛰고 정상 진행한다.

## 3. 후보 선정

후보는 두 갈래에서 뽑는다. **둘을 합쳐 상위 8건**을 고른다.

- **(가) 새 서식** — 카탈로그에 같은 뜻의 문서가 아예 없는 것
- **(나) 계열 변형** — 이미 있는 서식의 **실무 변형**. 같은 이름이어도 상황이 다르면 다른 서식이다.
  예: 용역계약서 → 업종별(디자인·개발·강의·청소), 위임장 → 용도별(부동산·차량·금융·관공서),
  견적서 → 업종별, 확인서 → 발급 목적별, 각 서식의 간이형/상세형·개인용/법인용.
  변형은 `series`·`variant`·`variant_use` 를 채워 계열로 묶는다(SPEC_GUIDE 참조).

| 항목 | 배점 | 판단 기준 |
|---|---|---|
| 수요 | 35 | 검색량·질문 빈도 |
| 분류 채우기 | 30 | 서식이 적은 중분류를 채우는지 (아래 규칙) |
| 제작 난도(역산) | 20 | 블록 조합으로 정확히 만들 수 있는지 |
| **시즌 가중치** | 0 / 10 / 20 | `season.py` 결과: 후보가 **선행 구간** 시즌의 키워드와 맞으면 **+20**, 시즌 중이면 +10, 무관하면 0. 여러 시즌에 걸리면 가장 높은 점수 하나만 |

**시즌 가중치의 목적.** 검색 수요가 오른 뒤에 만든 페이지는 색인이 끝나기 전에 시즌이 지나간다.
그래서 **시즌 중(+10)보다 선행 구간(+20)을 더 높게** 준다. 선행 구간 시즌이 있는 날은
그날 만드는 5종 중 **최소 1종**을 그 시즌 후보에서 뽑는다(분류 채우기 2종 규칙과 겹쳐도 된다).

**분류 채우기 배점 규칙** (실행 시점의 `catalog.json` 으로 매번 계산한다):

| 그 중분류의 현재 서식 수 | 배점 |
|---|---|
| 0~5종 | 30 |
| 6~15종 | 20 |
| 16~25종 | 10 |
| 26종 이상 | 0 |

서식 수가 가장 적은 중분류 3개는 **그날 만드는 5종 중 최소 2종**을 여기서 뽑는다.

## 4. 자체 검수 (승인 절차 없음)

사람의 승인을 기다리지 않는다. 대신 **상위 8건 중 아래를 모두 통과한 것만** 최대 5종까지 만든다.
하나라도 걸리면 그 후보를 버리고 다음 후보로 넘어간다.

| 검수 항목 | 통과 기준 |
|---|---|
| 중복 | `catalog.json` 에 **똑같이 쓰이는** 서식이 없다. 쓰는 상황·항목 구성이 다르면 중복이 아니다 — 계열 변형(3절 나)은 중복으로 보지 않는다. 판단이 애매하면 기존 서식의 `outline`(들어 있는 항목)과 비교해 **항목이 3개 이상 다르면 별개 서식**으로 본다 |
| 저작권 | 특정 기업·기관의 등록 서식을 베끼는 것이 아니다 |
| 법정 서식 | 관공서 제출용 법정 신고서식이 **아니다**. 원본 별지 서식이어야 효력이 있는 문서는 만들지 않고, 대신 정부24 등에서 받으라고 안내할 대상이다 |
| 개인정보 | 주민등록번호·건강·종교·정치성향 기재란이 필요 없는 서식이다 |
| 제작 가능성 | SPEC_GUIDE의 블록 조합으로 1~2페이지에 정확히 담을 수 있다 |
| 실용성 | 실제로 손으로 채워 제출하는 문서다 (안내문·홍보물이 아니다) |

통과 건수가 5종에 모자라면 **거기서 멈추지 말고** 3절 (나) 계열 변형으로 나머지를 채운다.
계열 변형은 기존 서식의 항목 구성을 바꾸는 작업이라 후보가 마르지 않는다.

그래도 0건이면(도구 고장 등) 사유를 남기고 정상 종료한다. **"만들 것이 없다"는 사유로는
0건 종료하지 않는다** — 그 상황은 계열 변형으로 채우라는 뜻이다.

## 5. 생성

검수를 통과한 서식마다 다음을 수행한다.

1. `specs/{id}.yaml` 작성 — `SPEC_GUIDE.md`의 블록 문법을 정확히 따른다.
   `id`는 영문 소문자·하이픈, 파일명과 일치. `featured: false`.
   - **미리보기 예시값(sample)** 은 3-1절 규칙대로 반드시 넣는다.
   - **상세 화면 본문 `howto`·`faq`** 도 3-2절 규칙대로 반드시 넣는다
     (howto 3~5단계·각 60자 이내, faq 2~4문항·질문 34자 이내). 계열 서식이면 `variant_use`까지.
     이 세 가지가 체류시간과 검색 유입을 만드는 부분이라 빠뜨리면 페이지가 비어 보인다.
   - **`related` 2~4개** 도 3-3절 규칙대로 넣는다. 제목이 비슷한 것이 아니라
     **그 서식을 쓴 사람이 바로 다음에 필요로 할 서식**의 id를 적는다.
     같은 계열(series)의 서식은 넣지 않는다.
   - `catalog/collections.json`의 주제 모음 중 새 서식이 들어갈 자리가 있으면
     흐름 순서에 맞게 `ids`에 끼워 넣는다 (3-4절). 맞는 모음이 없으면 그냥 둔다.
2. `python scripts/check_spec.py {id}` — **[통과]** 가 나올 때까지 수정한다.
3. `python scripts/build_form.py {id}` — 다음을 확인한다.
   - `[완료] 1p` (목표 페이지 이내)
   - `[경고]` 가 있으면 원인을 해결한다 (항목 누락·개인정보·파일 크기)
   - 목표 페이지를 넘기면 `python scripts/fit_one_page.py {id}` 로 보정한다
4. 생성된 `public/files/{id}/preview-1.webp` 를 **직접 열어 눈으로 확인한다.**
   표가 깨졌거나 칸이 비정상적으로 크면 명세를 수정하고 다시 빌드한다.

## 5-1. 정보형 가이드 1편 (서식 생성 뒤)

서식 5종을 끝낸 뒤 가이드 1편을 쓴다. 규칙 정본은 `scripts/agent/GUIDE_SPEC.md` 다.

1. **주제 선정** — 아래 순서로 1건을 고른다.
   - (1순위) **선행 구간 시즌**(`season.py` 의 `선행 +20점`)의 절차·계산법 주제 — 오늘 만든 서식과 연결되면 더 좋다.
     단, 같은 시즌 가이드가 `guides/` 에 이미 2편 이상이면 이 순위를 건너뛴다(한 시즌에 몰리지 않게)
   - (2순위) 오늘 만든 서식이 속한 **일의 앞 단계**를 설명하는 주제 (예: 내용증명 서식을 만들었다면 "내용증명 보내는 법과 효력")
   - (3순위) 가이드가 아직 **한 편도 연결되지 않은 인기 서식**의 앞 단계 주제
   - (4순위) 시즌 중(+10점) 시즌의 주제
   - `guides/` 의 기존 제목과 **검색 의도가 같으면 버린다** (표현만 다른 같은 글 금지)
2. **1차 출처 조사** — GUIDE_SPEC 4절의 기관 사이트에서 숫자·기한·조문을 확인하고 `sources` 에 적는다.
   출처를 못 찾은 숫자는 쓰지 않는다
3. **작성** — `guides/<slug>.yaml`. 연결 서식 2~4종(오늘 만든 서식 포함 권장), 본문 공백 제외 1,200자 이상
4. **검산** — 본문의 계산 예시는 `python -c` 로 직접 계산해 확인한다
5. 빌드 알림에 `[가이드] <slug>:` 가 찍히면 고칠 때까지 반복한다

가이드는 **서식 생성이 실패해도 따로 진행**한다. 반대로 가이드가 검증을 통과하지 못하면
가이드 파일만 지우고(`git rm` 하지 말고 파일 삭제) 서식은 정상 커밋한다. 가이드 때문에 서식 배포를 멈추지 않는다.

## 6. 검증·배포

```bash
python scripts/build_site.py
python scripts/validate_catalog.py     # 오류 0건이어야 한다 (가이드 규칙 위반·JSON-LD 파싱 실패도 오류)
git add -A
git commit -m "feat(forms): add {id1},{id2} + guide {slug} [agent]"
git push

# 푸시 직후 IndexNow 통보 — 빙·네이버·Yandex 에 새 서식을 즉시 알린다(구글은 미지원).
# 오늘 등록한 id 만 지정한다. --recent 를 쓰면 메타 일괄 수정 때 엉뚱한 것이 섞인다.
python scripts/ping_indexnow.py --ids {id1},{id2}
# 오늘 쓴 가이드와 가이드 허브
python scripts/ping_indexnow.py --paths /guide/{slug}/,/guide/
```

푸시하면 `deploy-pages` 워크플로가 자동으로 깨어나 GitHub Pages에 반영한다(약 1~2분).
**배포 확인을 위해 기다리지 않는다.** 러너 시간을 쓰지 않기 위해 푸시로 끝내고,
반영 여부는 다음 실행의 첫 단계에서 아래로 확인한다.

- `https://freeforms.kr/form/{전날 추가한 id}/` 가 200
- `.pdf` `.docx` `.hwpx` 3개 파일이 모두 200
- 200이 아니면 리포트에 "전날 배포 미반영"으로 적고 원인을 조사한다

**IndexNow 통보에 대하여.** 통보를 보내는 시점에는 아직 배포가 끝나지 않았을 수 있다.
검색엔진은 곧바로 오지 않고 뒤에 다시 시도하므로 문제가 되지 않는다. 통보가 실패해도
**배포를 되돌리거나 실행을 중단하지 않는다** — 검색 노출이 조금 늦어질 뿐이다.
실패하면 리포트에 한 줄로 적는다. `403`이 나오면 키 파일
(`https://freeforms.kr/<INDEXNOW_KEY>.txt`)이 사라진 것이므로 그 사실을 보고한다.

## 7. 리포트

실행 요약을 **한국어로 화면에 출력**한다(GitHub Actions 실행 로그에 남고, 관리자에게
메일 알림으로도 간다). 동일 내용을 `logs/YYYY-MM-DD.md`에 저장해 같은 커밋에 포함한다.

```
[무료서식 일일 리포트] 2026-00-00 (목) 08:42 KST
밀린 요청: 1건 처리  검수 통과: 2/5  생성: 3  실패: 0  푸시: 완료
 1) 거래처등록신청서 (기업·영업·마케팅)  /form/vendor-registration/
 2) 상가임대차계약서 (부동산·임대·매매)  /form/commercial-lease-contract/
가이드: 상가 임대차 계약 전 확인사항  /guide/commercial-lease-checklist/  (연결 서식 3종 · 출처 3건)
시즌: 선행 — 연차 사용 촉진(22일 전) / 시즌 중 — 이사철  · 오늘 시즌 후보 반영 1종
다음날 재검토 후보: 지급명령신청서, 반성문, 진료 동의서
카탈로그 합계: 48종 / 배포 파일: 284개
```

### 7-1. 지표 (매일)

워크플로가 에이전트 실행 **전에** `scripts/report_metrics.py` 로 지표를 뽑아
`logs/_metrics_today.md` 에 써 둔다(커밋하지 않는 임시 파일 — `.gitignore` 대상).
**그 파일 내용을 리포트 맨 아래에 그대로 붙인다.** 숫자를 고치거나 추정하지 않는다.
파일이 없거나 "지표 미연결"이면 그 한 줄만 적는다.

지표 항목: 최근 24시간 방문자 · 다운로드 수(형식별) · **검색 유입 상위 검색어 5개**(서치콘솔, 3일 지연) ·
**가이드 조회 상위 3편** · **가이드→서식 전환율**(`guide_to_form` ÷ `guide_view`) · 상세→가이드 카드 클릭(`article_card_click`) ·
네이버 블로그 유입(있을 때만)

매주 월요일에는 리포트에 다음을 추가한다.

- `report_metrics.py --weekly` 가 만든 **주간 지표표**(실행계획서 2절: 검색 유입 세션·평균 참여 시간·세션당 페이지·가이드→서식 전환·블로그 유입).
  색인 페이지 수는 API로 받을 수 없으므로 "서치콘솔에서 수동 확인" 으로 둔다

- 카테고리별 서식 수와 비어 있는 중분류
- (통계 연동 후) 주간 인기 서식 상위 10종과 결과 없는 검색어
- 대표 서식 10종 교체 제안 (다운로드 순위 기준)

## 8. 안전장치 (반드시 지킬 것)

- **생성 상한**: 서식 하루 5종·주 30종, 가이드 하루 1편·주 7편을 넘기지 않는다.
- **가이드 정확성**: 숫자·기한·요율·조문은 1차 출처(법령·기관)에서 확인한 것만 쓰고 `sources` 에 남긴다.
  출처를 댈 수 없는 숫자는 쓰지 않는다. 서식 상세의 howto·faq 문장을 복사하지 않는다(중복 콘텐츠).
- **검수 없는 게시 금지**: 4절 검수를 통과하지 못한 서식을 `status: published`로 올리지 않는다.
- **저작권**: 특정 기업·기관의 등록 서식을 복제하지 않는다. 상용 서식 사이트의 파일을
  가져오지 않는다. 법정 서식은 법령 별지 서식을 참고하고 `source: law-standard`와
  `source_note`에 근거 법령을 적는다.
- **개인정보**: 주민등록번호 항목을 만들지 않는다(빌드 검수에서 차단됨). 건강·병력·종교·
  정치성향 등 민감정보 기재란을 새로 만들지 않는다.
- **법률 판단 금지**: 서식 틀만 제공한다. 본문에 단정적인 법률·세무 판단을 쓰지 않고,
  필요하면 `notice`로 "제출처·법령 기준을 확인하십시오" 수준으로 안내한다.
- **비밀정보**: 토큰·키를 커밋 내용·리포트·로그에 남기지 않는다.
- **롤백**: 문제 서식이 발견되면 명세의 `status`를 `retired`로 바꾸고 재빌드·재배포한다.
  파일은 남기고 노출만 중단된다.
- **분기 점검**: 매 분기 첫 실행 시 `source: law-standard` 서식의 근거 법령 개정 여부를
  점검하고, 개정이 있으면 리포트에 보고한다. 같은 날 `guides/` 의 연도가 들어간 수치(최저임금·요율 등)도
  점검해 바뀐 값이 있으면 고치고 `updated_at` 을 갱신한다.

## 9. 실패 시 처리

- 생성 실패: 1회 재시도한다. 재실패하면 해당 서식을 건너뛰고 사유를 리포트에 적고,
  다음 날 후보로 재상정한다.
- 검증 실패(`validate_catalog.py` 오류): **커밋하지 않는다.** 원인을 리포트하고 종료한다.
- 푸시 실패: 원격이 앞서 있으면 `git pull --rebase` 후 재시도한다. 그래도 실패하면
  커밋을 남긴 채 사유를 리포트하고 종료한다(다음 실행에서 이어서 푸시된다).
- 전날 배포 미반영 확인: 리포트에 적고, `deploy-pages` 워크플로 실행 기록을 확인한다.

## 10. 로컬 정본 동기화

에이전트는 GitHub에 직접 커밋한다. 따라서 **원격이 앞서고 로컬 정본이 뒤처진 상태**가 된다.
관리자가 로컬에서 `.\deploy_forms.ps1 -Pull` 을 실행하면 그 결과가 `C:\Project_Forms`에 반영된다.

**최종 정본은 항상 로컬**이라는 원칙을 유지하기 위해, 리포트 말미에
"로컬 동기화 필요: `.\deploy_forms.ps1 -Pull`" 한 줄을 항상 포함한다.

⚠️ 관리자가 로컬에서 작업할 때는 **먼저 당겨오고 시작해야** 충돌이 나지 않는다.
